- `[入力]`、`XX.X`、`代表例を入力`の箇所だけ、追加実験の結果へ置き換えてください。
- 発表本番では、コードを全文説明せず、**課題・方法・結果・考察**を中心に話します。
- メインは9枚で約10分です。Appendixは質疑応答用です。

# Slide 2　背景と課題（0:30–1:40）

## スライドに貼る内容

### 背景

- AIエージェントは、外部ツールを使って計算・検索・変換などを実行する
- **どのツールを、いつ、どの順番で使うか**が回答品質に影響する

### 課題

- 最終回答が正しくても、ツールを使っていない場合がある
- 簡単な問題では、LLMが自力で答えられるため改善差が見えにくい
- 手動で指示文を調整すると、モデル変更後も再調整が必要になる

### 問い

**ツール利用を評価し、DSPyで指示文の改善を自動化できるか？**

## 読み上げ原稿

背景として、AIエージェントはLLMだけで回答するのではなく、外部ツールを利用できます。しかし、重要なのはツールが存在することだけではなく、どのツールを、どの順番で使うかです。例えば、単位をそろえずに平均を計算すると、最終回答が誤ります。また、簡単な計算はLLMが自力で答えられるため、回答だけを見てもツール利用の良し悪しを判断できません。そこで、ツールの種類、順序、引数、回答を評価し、その改善をDSPyで自動化できるかを調べました。

## 図の意図

スライド右側の流れは「質問→ツール選択→実行→回答」です。中央の「選択・順序」を強調します。

# Slide 3　DSPy・ReAct・GEPAの役割（1:40–2:55）

## スライドに貼る内容

### DSPy

LLMアプリを「入力・出力・評価・最適化」の部品として記述

### ReAct Agent

```text
考える → ツールを呼ぶ → 結果を見る → 次の行動
```

実行履歴 `trajectory` にツール名・引数・結果を記録

### GEPA

```text
Agent実行
  ↓
Judgeが score + feedback
  ↓
Reflection LMが改善案
  ↓
新しい指示文を評価
```

**モデルの重みではなく、主にAgentの指示文を改善**

## 読み上げ原稿

今回使用したDSPyは、LLMアプリをPythonの部品として記述し、評価指標を使って最適化するフレームワークです。エージェント部分にはReActを使いました。ReActは、考える、ツールを呼ぶ、結果を見る、という処理を繰り返し、その履歴をtrajectoryとして返します。最適化にはGEPAを使いました。別のJudge LMが実行を採点し、文章のフィードバックを返します。GEPAはそのフィードバックを基に新しい指示文を提案し、より良い候補を選びます。ここで学習しているのはモデルの重みではなく、主にエージェントへ与える指示です。

## 補足

「GEPAはプロンプト最適化」と短く言って構いませんが、発表では「DSPyプログラムの指示文を改善」と表現すると正確です。

# Slide 4　実験構成と評価方法（2:55–4:25）

## スライドに貼る内容

### 利用可能な3ツール

| ツール | 役割 |
|---|---|
| `calculate_expression` | 1つの数式 |
| `analyze_numbers` | 平均・中央値など |
| `convert_units` | km→m、kg→gなど |

### 評価の流れ

```text
質問 → ReAct Agent → trajectory
                     ↓
       Judge LM + 期待ツール順序
                     ↓
             score + feedback
```

### 総合点

- ツール選択：40%
- 必要性：20%
- 引数：15%
- タスク達成：25%

### データ分割

`train 8問 / validation 4問 / test 8問 / 1ツール対照 3問`

## 読み上げ原稿

利用できるツールは、数式計算、統計分析、単位変換の3つです。ReActのtrajectoryから、実際に使ったツール名、引数、結果を取り出しました。Judge LMには、質問、実行履歴、参照回答に加えて、今回の制御実験で期待するツール順序も渡しました。採点は、メンターから示されたツール選択40%、必要性20%、引数15%、タスク達成25%の重みを使用しました。さらに、総合点とは別に、期待したツール列と完全に一致した割合を測りました。最適化に使うtrainとvalidation、最後だけ使うtest、簡単な性能を守るための1ツール対照を分けました。

## 注意

追加実験の問題数を変更した場合は、最後の行を実際の件数へ直してください。

# Slide 5　予備実験の結果（4:25–5:40）

## スライドに貼る内容

### 1ツール問題

```text
計算 / 統計 / 単位変換
```

最適化前から正しいツールを選択  
→ **GEPA後も明確な改善なし**

### 2ツール問題の一例

質問：`1.2 km、800 m、1500 mの平均をmで求める`

```text
期待      convert_units → analyze_numbers

最適化前  calculate_expression

GEPA後    convert_units → calculate_expression
```

**総合スコア：約 +1ポイント**

### 解釈

単位変換は追加されたが、統計ツール選択までは改善せず  
→ **部分的な改善**

## 読み上げ原稿

まず予備実験です。計算、統計、単位変換を1つだけ使う問題は簡単で、最適化前から正しいツールを使っていました。そのため、GEPAを回しても明確な改善は見られませんでした。一方、1.2キロメートル、800メートル、1500メートルの平均問題では、最適化前は計算ツールだけでしたが、GEPA後は単位変換の後に計算ツールを使うようになり、総合スコアは約1ポイント上がりました。ただし期待したのは単位変換の後に統計ツールを使う手順です。したがって、完全な改善ではなく、単位をそろえる行動だけが追加された部分的改善と解釈しました。

## 話し方

ここは今回の発表で重要です。「改善した」と強く言い切らず、何が改善し、何が未達だったかを分けて説明します。

# Slide 6　追加実験：問題を複雑化（5:40–7:00）

## スライドに貼る内容

### 仮説

**複数の中間結果を次のツールへ渡す問題なら、改善余地が見えやすい**

### 難易度を段階化

```text
1ツール       convert
2ツール       convert → calculate
3ツール       convert → analyze → calculate
4ツール       convert → convert → analyze → calculate
```

### 代表問題

`2.5 kg、750 g、1.25 kgの中央値をgで求め、100 gを引く`

```text
convert_units → convert_units
             → analyze_numbers
             → calculate_expression
```

### 実験上の工夫

- 期待ツール順序と参照手順を各問題に付与
- testはGEPAへ見せない
- 1ツール対照で副作用も確認

## 読み上げ原稿

予備実験から、1ツール問題では改善の余地が小さいと考えました。そこで追加実験では、2回から4回のツール利用が必要な問題を作りました。代表例では、2つのキログラム値をグラムへ変換し、中央値を統計ツールで求め、最後に100グラムを計算ツールで引きます。単に正解するだけではなく、前のツール結果を次のツールへ正しく渡す必要があります。また、各問題に期待ツール順序と参照手順を付け、test問題はGEPAに見せません。複雑問題だけに強くなり、単純問題で余計なツールを使う副作用がないかも、1ツール対照で確認します。

# Slide 8　考察と限界（8:30–9:25）

## スライドに貼る内容

### 分かったこと

1. **最終回答だけではツール利用品質を評価できない**
2. 難易度が低いと天井効果で改善が見えない
3. `score`だけでなく具体的な`feedback`が最適化に必要
4. 複雑問題では「種類・順序・中間値」を分けて見る必要がある

### 限界

- 問題数が少なく、長さ・重さ・時間の人工問題が中心
- LLM Judgeの採点にはばらつきがある
- GEPAの探索予算とAPIコストに制約
- コスト・応答時間・安全性は未評価

## 読み上げ原稿

考察です。第一に、最終回答が正しいだけでは、ツールを使ったか、正しい順序だったかは分かりません。第二に、簡単な問題では最適化前から高得点となり、天井効果で差が見えませんでした。第三に、GEPAには数値スコアだけでなく、どのツールが不足したかを示す具体的なfeedbackが重要です。一方、今回の問題は人工的で件数も少なく、Judgeのばらつきや探索予算の影響があります。また、実運用で重要なコスト、応答時間、安全性までは評価していません。

# Slide 9　結論と適用可能性（9:25–10:00）

## スライドに貼る内容

### 結論

- DSPyで、**ツール履歴の観測 → 評価 → GEPA最適化**を一連で実装できた
- 1ツール問題では改善余地が小さく、複数ツール問題で差を観測しやすかった
- 改善の判定には、総合点だけでなく**ツール順序完全一致率**が有効だった

### 東芝のAIエージェント開発・運用への示唆

```text
モデル・プロンプト更新
        ↓
回帰評価でツール利用の悪化を検知
        ↓
GEPAで指示改善候補を自動探索
        ↓
人間が安全性・コストを確認して採用
```

**適用可能性はあるが、業務データ・人手評価・運用指標での追加検証が必要**

## 読み上げ原稿

結論です。DSPyを使い、ReActのツール履歴を観測し、Judgeで評価し、GEPAで指示文を改善する流れを実装できました。1ツール問題は最初から性能が高く、複数ツール問題の方が差を観測しやすいことが分かりました。また、総合点だけでなく、ツール順序完全一致率を併用することで、部分的改善を区別できました。将来的には、モデルやプロンプト更新後の回帰評価と、改善候補の自動探索へ適用できる可能性があります。ただし、実際の業務データ、人手評価、コスト、安全性を含む追加検証が必要です。以上です。

# Appendix 2　評価式（質疑応答用）

## スライドに貼る内容

### ツール選択点

```text
0.5 × 期待順序との位置一致
+ 0.5 × Judgeの選択評価
```

### 総合点

```text
0.40 × ツール選択
+ 0.20 × 必要性
+ 0.15 × 引数
+ 0.25 × タスク達成
```

### 別指標

```text
ツール順序完全一致率
= 期待ツール列と実際の列が完全一致した問題の割合
```

## 質疑応答用メモ

LLM Judgeだけに依存すると、代替手段へ寛容になりすぎる場合があります。そこで、制御実験として期待ツール列との機械的な位置一致をツール選択点へ組み込みました。一方で、引数や最終回答は文脈を考慮できるJudgeで評価しています。
