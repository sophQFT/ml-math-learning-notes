Day 1 — DSPyの全体像

LM ↓ Signature 何を入力して何を出力するか ↓ Module どう実行するか ↓ Tool / ReAct 外部機能を使うAgent ↓ Prediction 実行結果 ↓ Metric 良し悪しを数値化 ↓ Optimizer Metricが良くなるようcompile

1. Signature

Signature = LLMにやらせたい仕事の入出力仕様。

class QA(dspy.Signature):
    """質問に簡潔かつ正確に答える。"""

    question: str = dspy.InputField()
    answer: str = dspy.OutputField()

questionが入力、answerが出力。class-based Signatureのdocstringはtask instructionsとして利用される。

2. Module

Signatureが「何をするか」なら、Moduleは「どうやってするか」。

predictor = dspy.Predict(QA)
predictor = dspy.ChainOfThought(QA)
agent = dspy.ReAct(QA, tools=[...])

3. Tool

def calculator(x: int, y: int) -> int:
    """2つの整数を加算する。"""
    return x + y

普通のPythonとしてはdef calculator(x, y):でも動く。しかしDSPyはToolの関数名、引数、型、docstringを読み、LMにToolの仕様として提示する。

型ヒントを書くこと自体がDSPyではない。 Toolを構造化してAgentに渡し、さらに評価と最適化まで行えるのがDSPyの枠組み。

4. ReActとtrajectory

thought ↓ tool_name ↓ tool_args ↓ Tool実行 ↓ observation ↓ 次のthought ... ↓ finish
agent = dspy.ReAct(
    QA,
    tools=[calculator],
    max_iters=5
)

pred = agent(question="100と250を足してください")
print(pred.answer)
print(pred.trajectory)

5. MetricとOptimizer

def metric(example, pred, trace=None):
    return example.answer == pred.answer

Metricは「良いとは何か」を定義するPython関数。OptimizerはMetricが改善するようinstructions、demos、場合によってはweightsを調整する。

optimizer = dspy.BootstrapFewShot(metric=metric)

optimized_agent = optimizer.compile(
    agent,
    trainset=trainset
)

Day 2 — ツール利用最適化への実装

[1] Toolが必要か [2] 正しいToolか [3] 引数は正しいか [4] 順序は正しいか [5] Tool結果を回答に使ったか [6] 不要な呼び出しをせず終了したか

1. Baselineを先に作る

Baseline Agent ↓ 評価 ↓ Failure Analysis ↓ Metric設計 ↓ Optimizer.compile() ↓ 再評価 ↓ Before / After
def add_numbers(x: int, y: int) -> int:
    """Add two integers and return the sum."""
    return x + y

def multiply_numbers(x: int, y: int) -> int:
    """Multiply two integers and return the product."""
    return x * y

class ToolQA(dspy.Signature):
    """Use tools when necessary and answer accurately."""
    question: str = dspy.InputField()
    answer: str = dspy.OutputField()

agent = dspy.ReAct(
    ToolQA,
    tools=[add_numbers, multiply_numbers],
    max_iters=5,
)
example = dspy.Example(
    question="12と30を足してください。",
    answer="42",
    expected_tool="add_numbers",
    max_tool_calls=1,
).with_inputs("question")

expected_toolはTool利用評価用に自分で追加する教師ラベル。

2. trajectoryからToolを取り出す

def get_used_tools(pred):
    used_tools = []

    for key, value in pred.trajectory.items():
        if key.startswith("tool_name_") and value != "finish":
            used_tools.append(value)

    return used_tools

Argument accuracy引数が正しいか

Avg. tool calls効率
Latency / cost運用性能
def tool_choice_metric(example, pred, trace=None):
    used_tools = get_used_tools(pred)

    if example.expected_tool == "none":
        return len(used_tools) == 0

    if len(used_tools) == 0:
        return False

    return used_tools[0] == example.expected_tool

複合Scoreの例

S = 0.6 × Answer + 0.4 × Tool − 0.05 × ExtraCalls

重みは例。実際には「何を良いAgentと定義するか」自体が評価設計の中心。

5. 実験案

  • 曖昧なTool名/docstring vs 明確なTool名/docstring。
  • 似たToolを複数置いたときの選択性能。
  • Tool不要問題を増やしたときの過剰利用。
  • 引数の型・名前・Literal制約の影響。
  • max_itersと性能・呼び出し回数・遅延の関係。
  • Baseline vs BootstrapFewShot / GEPA / MIPROv2 / SIMBA。

6. デバッグ順序

  1. DSPyバージョン確認。
  2. Toolを単体実行。
  3. 1問だけAgent実行。
  4. pred.answer確認。
  5. pred.trajectory確認。
  6. expected toolとactual toolを並べる。
  7. Metricを単体実行。
  8. 複数問Baseline評価。
  9. 最後にOptimizerをcompile。
