# スライド2　背景：AIエージェントではツール利用が重要

## 画面に載せる内容

### ツールの選択と実行順序が回答品質を左右する

AIエージェントは、LLMと外部ツールを組み合わせてタスクを実行する。

- 数値計算
- 統計分析
- 単位変換

適切なツール利用は、次の要素に影響する。

`回答の正確性　／　処理コスト　／　応答時間`

## 話す内容（約50秒）

LLMは文章を生成するだけでなく、外部の計算機能やデータベースなどを呼び出すことで、より正確にタスクを処理できます。しかし、ツールを用意するだけでは不十分です。どのツールを使うか、どの引数を渡すか、複数のツールをどの順番で使うかを判断する必要があります。この判断は、回答の正確性だけでなく、コストや応答時間にも関係します。

## 図・配置

中央に次の流れを配置する。

`ユーザーの質問 → AIエージェント → 外部ツール → 最終回答`

# スライド3　課題：プロンプトの手動調整には限界がある

## 画面に載せる内容

### ツール選択を人手だけで改善するのは難しい

従来の改善サイクル

1. エージェントを実行する
2. 失敗例を確認する
3. 人がプロンプトを書き換える
4. 再び評価する

問題点

- 調整に時間がかかる
- 改善が担当者の経験に依存する
- 問題やモデルが変わると再調整が必要になる

## 話す内容（約50秒）

ツール選択を間違えた場合、人が実行履歴を確認し、「単位が混在しているときは先に変換する」といった指示をプロンプトへ追加できます。しかし、この方法は試行錯誤になりやすく、問題数やツール数が増えると負担が大きくなります。そこで今回は、評価データと評価基準に基づいてプロンプトを自動改善するDSPyを使用しました。

## 図・配置

「実行 → 評価 → 手動修正 → 再実行」の循環を矢印で示す。

# スライド4　DSPyとは何か

## 画面に載せる内容

### DSPyはLLMアプリケーションを構築・最適化するPythonフレームワーク

| 構成要素 | 今回の役割 |
|---|---|
| Signature | 入力・出力とタスクを定義 |
| Module | ReActで推論とツール実行を行う |
| Metric | 回答とツール利用を採点する |
| Optimizer | 高得点になる指示を探索する |

`データ ＋ Metric ＋ Optimizer → 最適化されたDSPyプログラム`

## 話す内容（約60秒）

DSPyは、LLMをプロンプトへ文章を入力して使うだけでなく、Pythonプログラムの構成要素として扱うフレームワークです。Signatureで入力と出力を定義し、Moduleで処理方法を決めます。今回は、推論しながらツールを選ぶReActを使用しました。さらに、何を良い実行とするかをMetricで定義し、Optimizerで高得点になる指示を探索します。これにより、人が細かなプロンプト表現を繰り返し調整する作業を自動化できます。

## 図・配置

# スライド5　3種類のツールを使うReActエージェントを構築した

## 画面に載せる内容

### 質問に応じて3種類のMCPツールから選択する

| ツール | 用途 | 例 |
|---|---|---|
| `calculate_expression` | 四則演算・累乗 | 25 × 16 |
| `analyze_numbers` | 平均・中央値 | 1, 2, 3, 4, 5の平均 |
| `convert_units` | 長さ・質量の変換 | 10 kmは何mか |

ReActの処理

`質問 → ツール選択 → 引数生成 → 実行結果の確認 → 最終回答`

## 話す内容（約55秒）

メンターから与えられた3種類のMCPツールを、DSPyのReActエージェントへ登録しました。単純な式はcalculate_expression、数値配列の統計処理はanalyze_numbers、単位変換はconvert_unitsが担当します。ReActは、質問を読み、使うツールと引数を決め、実行結果を確認して最終回答を生成します。必要であれば、この処理を複数回繰り返します。

## 図・配置

- 上半分に3ツールの表を置く。
- 下半分にReActの処理フローを置く。

## 画面に載せる内容

### 問題を複雑化し、ツールの実行順序も評価対象にした

| 分類 | 問題数 | 問題例 | 期待するツール列 |
|---|---:|---|---|
| 単一：計算 | 2 | 2の10乗を求める | `calculate_expression` |
| 単一：統計 | 2 | 2, 4, 6, 8, 10の中央値 | `analyze_numbers` |
| 単一：変換 | 2 | 2 kgは何gか | `convert_units` |
| 変換→計算 | 4 | 2 kmをmに直し、350 mを足す | `convert → calculate` |
| 変換→統計 | 4 | 1.2 km、800 m、1500 mの平均 | `convert → analyze` |

合計14問

## 話す内容（約70秒）

最初は、計算、統計、単位変換をそれぞれ1つのツールで解く問題だけを使いました。しかし、質問とツールの対応が明確で、Baselineの段階から高得点になりました。そこで、単位変換の結果を計算ツールまたは統計ツールへ渡す複数ツール問題を8問追加しました。最終的なtrainsetは、単一ツール6問、変換から計算4問、変換から統計4問の合計14問です。複数ツール問題では、ツールの種類だけでなく、順番と結果の受け渡しも必要になります。

# スライド7　GEPAが実行履歴とフィードバックから指示を改善する

## 画面に載せる内容

### BaselineとGEPA後を同じ評価基準で比較した

1. Baselineを14問で評価
2. Judge LMが実行結果を採点
3. Reflection LMが失敗原因を分析
4. GEPAが新しい指示候補を生成
5. 候補を再評価し、高得点の指示を採用

Judge LMの採点項目

- ツール選択
- ツールの必要性
- 引数と実行順序
- 最終回答の正しさ

## 話す内容（約65秒）

まず、最適化前のエージェントであるBaselineを14問で評価します。次にJudge LMが、ツール選択、必要性、引数と順序、最終回答を採点し、日本語のフィードバックを返します。Reflection LMは実行履歴とフィードバックから失敗原因を分析し、GEPAが新しい指示候補を作ります。候補を同じ基準で再評価し、高得点の指示を残します。今回の最適化上限は80 metric callsとしました。

## 図・配置

次の流れを横方向または円形に配置する。

`Baseline → 採点 → 振り返り → 指示改善 → 再評価`

# 付録3　Judge LMとReflection LMの違い

| LM | 役割 | temperature |
|---|---|---:|
| Judge LM | エージェントの実行結果を安定して採点 | 0.0 |
| Reflection LM | 失敗原因を分析し、改善案を提案 | 1.0 |

同じGPT-5.4-miniを使用しても、役割ごとに別の`dspy.LM`として設定する。

temperatureは、LLM出力のばらつきを調整する値である。Judgeでは採点を安定させるため0.0、Reflectionでは改善候補を探索しやすくするため1.0とした。ただし、temperatureを上げることがスコア改善を保証するわけではない。
