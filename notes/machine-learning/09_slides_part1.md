# 発表スライド 前半（0:00〜5:30）

10分発表の前半。

**やったことの概要**まで。

後半（結果・考察・まとめ）は別ファイル。

---

## 使い方

各スライドは3つに分かれている。

- **【スライドに書く】**
  → PowerPointにそのまま貼る
- **【図】**
  → PowerPointの図形で作る手順
- **【話す】**
  → 口で言う内容。スライドには書かない

**スライドに文章を書かないこと。**
書いてあることを読み上げるだけの発表は
聞き手が退屈する。
スライドは短い語句、
詳しい説明は口で言う。

### PowerPoint の設定

- フォントサイズは **24pt以上**
- 1スライド **1メッセージ**
- 箇条書きは **1行20字以内**
- 前半6枚 + 後半4枚 = **合計10枚**が目安

# スライド3 — 背景と課題

**時間: 0:50〜2:10（1分20秒）**

### 【スライドに書く】

```
背景
・AIエージェントは外部ツールを
  呼び出してタスクを解く
```

さらに右側か下に、課題の3点:

```
手作業の問題
① 属人的で再現性がない
② モデル更新のたびに壊れる
③ 評価と改善が回らない
```

### 【話す】

> まず背景です。
>
> 最近のAIエージェントは、
> 計算や検索といった外部ツールを
> 自分で呼び出してタスクを解きます。
>
> このとき、
> **どのツールをいつ、
> どんな引数で呼ぶか**が
> 回答の品質を大きく左右します。
>
> ところが、その制御は
> プロンプトの文章として
> 書かれているだけです。
>
> つまり改善しようとすると、
> 人間がプロンプトを書き直して、
> 目で見て確かめて、
> また書き直す、という
> 手作業のループになります。
>
> これには3つの問題があります。
>
> 1つめは属人的で再現性がないこと。
> 誰がどう直したかが残りません。
>
> 2つめは、LLMを新しいモデルに
> 更新すると、せっかく調整した
> プロンプトが壊れてしまうこと。
>
> 3つめは、評価と改善のループが
> 手動なので、LLMOpsとして
> 回らないことです。
>
> **この手作業を自動化できないか、
> というのが本テーマの出発点です。**

### 補足

# スライド4 — DSPyとは

**時間: 2:10〜3:30（1分20秒）**

### 【スライドに書く】

```
DSPy
= Declarative Self-improving Python

プロンプトを手で書く代わりに
入出力の契約をコードで宣言し
プロンプトは
最適化アルゴリズムに書かせる

スタンフォードNLP発のOSS
```

### 【図】従来 vs DSPy

PowerPointの図形で、
上下2段の流れ図を作る。

**上段（従来）**

```
人間 → プロンプトを手書き → エージェント
  ↑                              ↓
  └────── 目視で評価 ←───────┘
        （手動ループ・赤色）
```

**下段（DSPy）**

```
人間 → 評価指標を定義 → Optimizer
                            ↓
        エージェント ← プロンプト自動生成
            ↓
        自動で評価（自動ループ・青色）
```

作り方:
1. 「四角形」を並べて文字を入れる
2. 「矢印」でつなぐ
3. 上段のループを**赤**、
   下段を**青**にする
4. 上段に「手作業」、
   下段に「自動」とラベルを付ける

### 【話す】

> DSPyは
> Declarative Self-improving Python
> の略で、
> スタンフォードのNLPグループが
> 公開しているOSSです。
>
> 一言でいうと、
> **プロンプトを手で書くのをやめて、
> 入出力の契約をコードで宣言し、
> プロンプト自体は最適化
> アルゴリズムに書かせる**
> フレームワークです。
>
> 図の上が従来のやり方です。
> 人間がプロンプトを書き、
> 動かして、目で見て、また直す。
> このループが全部手作業です。
>
> 下がDSPyです。
> 人間がやるのは
> **「何を良しとするか」
> という評価指標を定義すること**
> だけで、
> プロンプトの生成と評価は
> 自動で回ります。
>
> DSPyが主張しているのは、
> 手で調整したプロンプトは
> 壊れやすく転用が効かない、
> ということです。
>
> LLMやデータを変えると
> 壊れてしまうので、
> そもそも人間が書くべきではない、
> という考え方です。

# スライド5 — DSPyの3つの部品

**時間: 3:30〜4:30（1分）**

### 【スライドに書く】

```
① Signature ― 入出力の契約
   何を入れて何を出すかを宣言

② Module ― 呼び出し戦略
   ReAct = ツールを繰り返し呼ぶ

③ Optimizer ― 自動最適化
   指示文と実例を自動で探索
```

### 【図】ReActの内部

右側か下に小さく:

```
   dspy.ReAct
   ┌──────────────┐
   │ react        │ ← 次に呼ぶ
   │              │   ツールを決める
   ├──────────────┤
   │ extract      │ ← 最終回答を
   │              │   合成する
   └──────────────┘
      ↑
   Optimizerは
   この2つの指示文を書き換える
```

最後の2行は**赤字で強調**。

### 【話す】

> DSPyの部品は3つだけです。
>
> 1つめが **Signature**。
> 何を入力して何を出力するか、
> という契約をコードで書きます。
> このとき書いた説明文が、
> そのままLMへの指示文になります。
>
> 2つめが **Module**。
> LMをどう呼ぶかの戦略です。
> 今回使ったのは **ReAct** という、
> 推論とツール呼び出しを
> 繰り返すモジュールです。
>
> 3つめが **Optimizer**。
> ここがDSPyの本体で、
> 評価指標と少数の例を与えると、
> 最も良い指示文と実例を
> 自動で探してくれます。
>
> ここで重要なのが右の図です。
>
> ReActの中身は実は2つの部品に
> 分かれていて、
> **次にどのツールを呼ぶかを
> 決める部分**と、
> **最終回答を作る部分**があります。
>
> Optimizerが書き換えるのは、
> この**両方の指示文**です。
>
> つまり
> 「いつ、どのツールを、
> どんな引数で呼ぶか」の判断基準
> そのものが自動調整される。
>
> **これが本テーマでいう
> 『ツール利用最適化』の実体です。**

### 補足

**この最後の3行が
前半で一番大事なメッセージ。**
ここだけは間を取ってゆっくり話す。

# スライド6 — 実装したもの

**時間: 4:30〜5:30（1分）**

### 【スライドに書く】

```
題材：Azure OpenAI + MCPサーバ
      3つのツールを持つエージェント

・calculate_expression  数式の計算
・analyze_numbers      配列の統計量
・convert_units        単位の変換
```

### 【図】システム構成

左から右への流れ図。

```
ユーザーの質問
     ↓
┌─────────────────┐
│  MCPToolAgent   │
│  (dspy.Module)  │
│    ↓            │
│  dspy.ReAct     │ ─→ MCPサーバ
│    ↓            │ ←─ （3ツール）
│  結果を整形     │
└─────────────────┘
     ↓
  最終回答
```

### 【話す】

> 実装したものを説明します。
>
> 題材は、Azure OpenAIをLMとして、
> MCPサーバ経由で3つのツールを
> 呼び出すエージェントです。
>
> ツールは、
> 数式を計算するもの、
> 数値の配列の統計量を出すもの、
> 単位を変換するもの、の3つです。
>
> DSPyでは、ツールは
> **説明文つきのPython関数を
> 渡すだけ**で登録できます。
> この説明文がそのまま
> LMへのツール説明になります。
>
> 図が全体の構成です。
>
> 質問が来ると、ReActが
> どのツールを呼ぶか判断し、
> MCPサーバに問い合わせて、
> 結果を見てまた考え、
> 最終的な回答を作ります。
>
> ここで一点、工夫があります。
>
> ReActをそのまま使うと、
> 実行の記録が扱いにくい形でしか
> 取り出せません。
>
> そこで **dspy.Module で
> ReActを包み**、
> 「どのツールを呼んだか」
> 「その結果は何か」を
> 取り出せる形に整えました。
>
> これが次に説明する
> 評価の仕組みで必要になります。

## 想定質問と答え（前半分）

**Q. LangChainなど他の
フレームワークとの違いは？**

> LangChainはツールの接続や
> 実行の枠組みを提供しますが、
> プロンプト自体は人が書きます。
> DSPyはそのプロンプトを
> 自動生成・自動改善する点が
> 異なります。
> 併用も可能です。

**Q. なぜReActを選んだのか？**

> ツールを使うエージェントの
> 代表的な方式で、
> DSPyに標準搭載されているためです。
> また内部が2つの部品に
> 分かれているため、
> 最適化の対象が明確で、
> 何が変わったかを説明しやすい
> という利点もありました。

**Q. MCPを使う必要はあったのか？**

> DSPyから見ると、MCPのツールも
> 「ただのPython関数」です。
> HTTPで社内サーバを呼ぶ関数を
> 渡しているだけなので、
> DSPy側の実装は変わりません。
> 逆に言えば、既存の社内ツールを
> そのままDSPyに載せられる、
> ということでもあります。
