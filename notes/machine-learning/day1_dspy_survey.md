# Day1 — DSPy の調査ノート

> テーマ: 「AIエージェントにおけるツール利用最適化技術の調査と評価」

## 0. 一行でいうと

**DSPy は「プロンプトを書く」のをやめて「入出力の契約をコードで宣言し、プロンプトは最適化アルゴリズムに書かせる」ためのフレームワーク。**

名前は **D**eclarative **S**elf-improving **Py**thon の略。スタンフォード NLP 発の OSS で、2026 年 8 月時点の最新は 3.3 系。

---

## 1. なぜ DSPy が必要なのか（実習の背景と直結）

課題文の整理:

| 現状 | 問題 |
|---|---|
| AIエージェントの品質はツールをいつ・どう使うかで決まる | その制御はプロンプトに書かれている |
| プロンプトは人手でチューニングしている | 属人的・再現性がない・工数がかかる |
| LLM を差し替えると壊れる | モデル更新のたびにやり直し |
| 評価と改善のループが手動 | LLMOps として回らない |

DSPy の主張は「**プロンプトエンジニアリングは壊れやすく転用が効かない**」というもの。LLM・パイプライン・データのいずれかを変えると、手でチューニングしたプロンプトは壊れる。だから DSPy は:

1. LM 呼び出しを、契約の定まった宣言的モジュールとして扱う
2. 最適化アルゴリズムで最良のプロンプトを自動探索する
3. 異なる LM 間でプログラムを持ち運べるようにする
4. ニューラルネットの学習に似た体系的な反復を可能にする

**これがそのまま「AIエージェントは評価の改善を手動で行う → DSPy で自動化」という実習テーマの中身。**

図式化するとこうなる。

```
従来:   人間 → プロンプト文字列を手書き → エージェント → 目視で評価 → 人間が書き直す
                                                              ↑____________________|
                                                                （手動ループ）

DSPy:   人間 → Signature（何を入れて何を出すか）
             → Module（ReAct 等の戦略）
             → Metric（何を良いとするか）
             → Optimizer が自動でプロンプトを探索
                                    ↑____________________|
                                      （自動ループ）
```

人間の仕事が「プロンプトを書く」から「**何を良しとするかを定義する（= メトリクス設計）**」に移動する。これが DSPy の本質であり、本実習で一番頭を使うところ。

## 2. DSPy の 3 層構造

覚えるべき概念はこの 3 つだけ。

### 2.1 Signature（入出力の契約）

モジュールの入出力の振る舞いを自然言語で記述したもの。たとえば `"question -> answer"` と書けば「質問を受け取って回答を返す」という指定になる。プロンプトを書く代わりに宣言だけすると、DSPy がそれを自動的にプロンプトへ展開する。

**書き方は 2 通り。**

```python
# (a) インライン記法 — 試すとき用
"question -> answer"
"question -> answer: float"          # 型を付けられる
"context, question -> answer"        # 複数入力
"document -> summary: str, score: float"  # 複数出力

# (b) クラス記法 — 本番用。docstring と desc で意図を伝えられる
class HelpdeskQA(dspy.Signature):
    """社内ヘルプデスクの問い合わせに、ツールを使って正確に回答する。"""

    question: str = dspy.InputField(desc="社員からの問い合わせ文")
    answer: str = dspy.OutputField(desc="日本語の簡潔な回答")
```

**重要な理解:** クラス記法の **docstring がそのまま LM への指示文になる**。そして最適化器が書き換えるのは、まさにこの指示文。だから初期値はあえて素っ気なく書いておき、最適化後にどう変わったかを比較するのが本実習の見どころになる。

### 2.2 Module（LM の呼び出し戦略）

Signature を受け取り、実際に LM をどう呼ぶかを決める部品。組み込みで以下がある。

| Module | 中身 | 使いどころ |
|---|---|---|
| `dspy.Predict` | 1 回呼ぶだけ。最小単位 | 単純な分類・抽出 |
| `dspy.ChainOfThought` | 思考過程 `reasoning` を出力に追加してから答える | 推論が要るタスク |
| `dspy.ReAct` | ツールを渡し、推論とツール呼び出しを繰り返す | **本実習の主役** |
| `dspy.ProgramOfThought` | Python コードを生成して実行させる | 計算・データ処理 |
| `dspy.MultiChainComparison` | 複数の思考を生成して比較 | 精度重視 |

これらを組み合わせてプログラムを作る。自作したければ `dspy.Module` を継承して `forward()` を書く。

### 2.3 Optimizer（旧 teleprompter）

**ここが DSPy の本体。** メトリクスと少数（10〜20 件程度）の訓練例を与えると、最適化器が最良の指示文・few-shot 例・設定をアルゴリズム的に自動探索する。

最適化器が調整する「パラメータ」は 3 種類:

1. **指示文（instructions）** — Signature の docstring から生成される自然言語の指示
2. **few-shot デモ（demos）** — プロンプトに埋め込む実例
3. **（BootstrapFinetune の場合）LM の重み** — 小型モデルのファインチューニング

| Optimizer | やること | コスト | 使いどころ |
|---|---|---|---|
| `BootstrapFewShot` | メトリクスを満たした実行例を few-shot デモとして採用 | 低 | **最初に必ずこれ** |
| `BootstrapFewShotWithRandomSearch` | 上のデモ組み合わせをランダム探索 | 中 | データが少し多いとき |
| `COPRO` | 指示文だけを座標上昇的に改善 | 中 | 指示文だけ直したいとき |
| `MIPROv2` | 指示文と few-shot 例を**同時に**最適化 | 中〜高 | **エージェント最適化の標準** |
| `GEPA` | 実行トレースを LM に振り返らせて指示文を提案 | 高 | 多目的・多モジュール |
| `SIMBA` | 出力のばらつきが大きい難例を選んで内省させる | 高 | データが多いとき |
| `BootstrapFinetune` | 重みそのものをファインチューニング | 最高 | 小型モデルへの蒸留 |

**実務的な選び方（はしご）:** BootstrapFewShot から始め、指示文とデモを一緒に詰める必要が出たら MIPROv2 か COPRO、多目的問題や複数モジュールのパイプライン、あるいは MIPROv2 が頭打ちになって計算量を注げるなら GEPA へ、という順に上る。多くの単一プロンプトのタスクは最初の 2 段から出ることがない。

#### MIPROv2 の中身（発表で説明できると強い）

3 段階で動く。

1. **few-shot 候補のブートストラップ** — 実際にプログラムを走らせ、メトリクスを満たした軌跡をデモ候補として集める
2. **指示文の提案** — タスクのデータとプログラム構造の両方を踏まえて指示文候補を生成する（data-aware かつ demonstration-aware）
3. **ベイズ最適化で組み合わせ探索** — `num_trials` 回の試行を回し、各試行で新しいプロンプト集合を検証セットで評価する。`minibatch=True` のときは各試行では `minibatch_size` 件のミニバッチだけで評価し、平均が最良のものを `minibatch_full_eval_steps` ごとに検証セット全体で評価する。最終的に検証セット全体で最も良かったプロンプト集合を返す

#### GEPA の中身

LM にプログラムの実行トレースを振り返らせ、何がうまくいき何が失敗したかを特定させて、そのギャップを埋めるプロンプトを提案させる。さらに**ドメイン固有のテキストフィードバック**を活用して急速に改善できる。

→ 本実習では「不要なツールを呼んでいる」「引数の型が違う」といった**ツール利用に特化した日本語フィードバック**をメトリクスから返してやれる。これは本テーマと相性が非常に良く、発表の目玉にできる（`code/metrics.py` の `metric_with_feedback` がその実装）。

## 3. ツール利用（本テーマの中核）

### 3.1 ツールの定義

DSPy でのツールは **型ヒントと docstring を付けただけの、ただの Python 関数**。

```python
def get_leave_balance(employee_id: str) -> dict:
    """社員IDから、その社員の有給休暇の残日数を取得する。

    引数は氏名ではなく社員ID (例: "E001")。氏名しか分からない場合は
    先に search_employee で社員IDを引くこと。
    """
    ...
```

- **docstring がそのまま LM への「このツールの説明」になる。**
- 型ヒントから引数スキーマが自動生成される。型ヒントが無いと LM が引数を間違えやすくなる。
- 「このツールを使うべきでない場面」まで docstring に書くのがコツ。

### 3.2 2 つの使い方

DSPy にはツール利用のアプローチが 2 つある。

1. **`dspy.ReAct`** — 推論とツール呼び出しを自動で処理する、完全に管理されたツールエージェント
2. **手動処理** — `dspy.Tool`、`dspy.ToolCalls` とカスタム signature を使って、ツール呼び出しのプロセスを直接制御する

本実習は 1 で十分。2 は「DSPy でどこまで細かく制御できるか」の調査項目として調べておくと、東芝への適用可能性の議論で使える。

### 3.3 ReAct の仕組み

ReAct は "Reasoning and Acting" の略で、ツールを使うエージェントを作るための代表的なパラダイム。言語モデルにツール一覧を反復的に与え、現在の状況について推論させる。モデルは推論の結果として、さらに情報を集めるためにツールを呼ぶか、それともタスクを終えるかを判断する。DSPy 版の ReAct は signature の多相性のおかげで任意の signature に対して動作する。

```python
react_agent = dspy.ReAct(
    signature="question -> answer",   # 入出力の指定
    tools=[tool1, tool2, tool3],      # 使えるツール
    max_iters=10                      # ツール呼び出しの最大回数
)
```

**内部構造（最適化の対象を理解するために重要）**

ReAct は 2 つの predictor から成る。

| predictor 名 | 役割 |
|---|---|
| `react` | 推論して、次にどのツールをどんな引数で呼ぶかを決める（`dspy.Predict`） |
| `extract.predict` | 集まった観測から最終出力を合成する（`dspy.ChainOfThought`） |

GEPA や MIPROv2 は**この両方の指示文を最適化する**。つまり「いつ・どのツールを・どんな引数で呼ぶか」の判断基準そのものが自動チューニングされる。**これが「ツール利用最適化」の実体。**

### 3.4 trajectory — 評価データの宝の山

ReAct の返り値 `pred.trajectory` は次の形の辞書になる。

```python
{
  "thought_0": "社員IDを調べる必要がある",
  "tool_name_0": "search_employee",
  "tool_args_0": {"name": "山田"},
  "observation_0": {"employee_id": "E001", ...},
  "thought_1": "...",
  "tool_name_1": "get_leave_balance",
  ...
}
```

押さえるべき挙動:

- キーは `thought_{i}` / `tool_name_{i}` / `tool_args_{i}` / `observation_{i}` の 4 点セット
- ReAct には終了用の組み込みツール **`finish`** があり、これが呼ばれるとループが終わる。自作ツールの呼び出し数を数えるときは除外すること
- ツールが例外を投げても落ちない。`observation_i` が `"Execution error in <tool名>: <traceback>"` という文字列になり、LM はそれを見て自己修正を試みる
- `max_iters` を超えるか、コンテキスト長超過・ツール選択失敗が起きるとループが打ち切られる

**Day4 の評価指標はほぼすべてこの trajectory から計算できる。**

## 4. 評価の設計（Day4 の予習）

単一の正答率だけでは弱い。ツール利用の評価は**粒度を分ける**のが定石。既存ベンチマークがちょうど 2 階層に分かれている。

| ベンチマーク | 測るもの |
|---|---|
| **BFCL**（Berkeley Function Calling Leaderboard） | 呼び出しレベルの正確さ。関数スキーマとクエリを与え、正しい関数を正しい引数で呼べるかを見る静的ベンチマーク |
| **τ-bench**（tau-bench） | タスクレベルの完遂率。小売・航空のリアルなシナリオを複数ターンのツール呼び出しにわたってシミュレートし、最終的にタスクが正しく完了したかを見る |

BFCL v4 はカテゴリ別に結果を分解する: simple function / multiple function / parallel function / parallel multiple function / **relevance detection**。「simple では高得点なのに parallel multiple で落ちる」なら改善対象が特定できる、という考え方。

**本実習で採るべき指標（`code/metrics.py` に実装済み）**

| 階層 | 指標 | 意味 |
|---|---|---|
| タスク | 回答正解率 | 最終的に正しく答えられたか |
| 呼び出し | ツール選択 **precision** | 呼んだツールのうち必要だったものの割合 = **余計なツールを呼んでいないか** |
| 呼び出し | ツール選択 **recall** | 必要なツールのうち実際に呼べたものの割合 |
| 呼び出し | ツール選択 **F1** | 上の調和平均 |
| 効率 | 平均ツール呼び出し回数 / ステップ効率 | 冗長さ |
| 効率 | 平均レイテンシ / トークン数 | 運用コスト |
| 頑健性 | ツール実行エラー率 | 引数生成の質 |

### 発表で光る論点: 「ツールは多いほど良いのか」

ある研究では、ReAct エージェントのツール数を 3 個から 10 個へ増やすと、最適化後の F1 が **U 字型のトレンド**を示し、ツールを増やすことが必ずしも最適化後の性能向上につながらなかったと報告されている。単一ツールの構成の方が、最適化の前でも後でも上位 10 ツール構成より強いケースすらあった。

→ 「ツール数 vs 性能」を 1 本の実験として入れると、**東芝の実運用への示唆（ツールは絞れ、docstring を磨け）**という結論に繋げられる。`code/tools.py` に `MINIMAL_TOOLS`（3 個）と `ALL_TOOLS`（5 個）を用意してあるのはこのため。

## 5. LLMOps 文脈での位置づけ（背景セクション用）

課題文の「LLMOps 技術」に接続するとこうなる。

| LLMOps の要素 | DSPy での対応 |
|---|---|
| ログ収集 | `pred.trajectory` / MLflow トレース |
| 評価データ作成 | `dspy.Example` のデータセット |
| 評価方法の検討 | メトリクス関数の設計（**人間の主な仕事**） |
| 課題発見 | 指標の分解（precision が低い = 余計なツール、など） |
| プロンプト改善 | Optimizer による自動探索 |
| 効果検証 | 最適化前後の同一 devset での比較 |

MLflow は DSPy とネイティブに統合された LLMOps ツールで、プロンプトや最適化の進行をトレースとして可視化できる。**実習では最初からこれを有効にしておくこと。** 各実行のトレースがノートブック上で見えるようになり、モデルの挙動への良い可視性が得られる。

## 6. Day1 のまとめ（発表スライド 1 枚ぶん）

- DSPy = プロンプトを書く代わりに、入出力の契約（Signature）と戦略（Module）を宣言し、メトリクスに基づいて最適化器がプロンプトを自動生成するフレームワーク
- ツールは docstring 付きの Python 関数。`dspy.ReAct` に渡すだけでエージェントになる
- ReAct の内部は「ツール選択の Predict」と「出力合成の ChainOfThought」の 2 つ。最適化器はこの両方の指示文を書き換える = **これがツール利用最適化の実体**
- 評価は呼び出しレベル（BFCL 型）とタスクレベル（τ-bench 型）の 2 階層で設計する
- 人間の仕事はプロンプト記述からメトリクス設計へ移る
